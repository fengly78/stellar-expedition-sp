## 二、对原审计 §一 表的修正

原表把「纳米厂」「晶体矿 g=1.6」等标为 `✅ 完全一致`，实际是**规则集与原版一致，但代码没实现到位**：

- 「纳米厂 1,000,000/500,000/100,000 g=2.0 ✅」→ 规则集确有 `BUILD.NANITE`（Candidate），
  但 `web/src/game/objects.ts` 的 `BUILDINGS` 表**无 id 34**，全仓库 `web/src` 搜「纳米/nanite」零命中。
  该建筑未实现，RC1 的 `BUILD.NANITE` 是一段无人消费的配置。
- 「晶体矿 48/24 g=1.6 ✅」→ 规则集与原版都是 1.6，**代码是 1.5**，与两者都不一致。
- 船坞/研究实验室 → 规则集与原版都是 g=2.0，**代码是 1.75**。

另：`doc/balance-content-check-2026-09-24.md` 视图 4 标题写「机器人/纳米=0」，即里程碑时间轴在
「假定纳米工厂存在但等级为 0」的前提下算的；代码里该建筑压根不存在，该表的适用范围需注明。

## 三、建筑时间公式：两套不同模型（非数值差异，是结构性差异）

| | 公式 | 出处 |
|---|---|---|
| 经典 0.84 | `T = 3600×(M+C) / (2500×(1+R) × 2^N × speed)`，**由造价推导** | `prod.php:104-111` |
| 冻结规则集 F-08 | `T = max(T_min, ceil(3600×(M+C)/(2500×(1+R)×2^N×speed)))`，同构 | `balance_rc1.json` F-08（Frozen） |
| 实际代码 | `T = baseTime × factor^L / SPEED / (1+R)`，**独立 baseTime 常量，不由造价推导** | `objects.ts:401-403` |

代码用「每种建筑一个手写 baseTime」替代了「造价决定时长」。RC1 声明 F-08 为 **Frozen**，
但生产实现根本没走 F-08。实测偏差（同 speed=4、机器人=0、纳米=0 口径）：

| 建筑 | 代码 (s) | 原版公式 (s) | 倍率 |
|---|---|---|---|
| 金属矿 | 15.0 | 27.0 | 1.80 |
| 晶体矿 | 15.0 | 25.9 | 1.73 |
| 太阳能 | 15.0 | 37.8 | 2.52 |
| 机器人工厂 | 15.0 | 187.2 | 12.48 |
| 船坞 | 15.0 | 216.0 | 14.40 |
| 聚变反应堆 | 22.5 | 453.6 | 20.16 |
| 月球基地 | 15.0 | 5760.0 | 384.00 |
| 跳跃门 | 15.0 | 2,160,000.0 | 144,000.00 |

代码里全部 Lv0 建筑都是 15.0s（仓库/船坞/实验室/铁塔/导弹井/月球基地/跳跃门同值），
即**造价昂贵的建筑和廉价建筑耗时相同**；原版下跳跃门比金属矿慢 8 万倍。
这不影响功能可用性（游戏能跑、门禁能过），但意味着 RC1 的 F-08 与 `BUILD.TIME` 在运行时是**装饰性的**。

**注**：`doc/balance-content-check-2026-09-24.md` 与 CR-002 附录 B 的 SIM 结论
（资产 188006 / 182659、仓损 0.095 / 0.081 等）是用 `rules/formulas.py` 的 F-08 模型离线算的，
**不是**用前端实际公式算的。因此那些 SIM 数字不能用来论证线上数值已校准。

### F-08 声明与线上实现矛盾（可复跑，`exit 1`）

`balance_rc1.json` 的 F-08 声明 `status: Frozen`、注释「上游同构式」，但线上根本不是这个公式：

| | 公式 |
|---|---|
| F-08 声明 | `T = max(T_min, ceil(3600*(M+C) / (2500*(1+R) × 2^N × speed)))` |
| 线上实现 | `T = baseTime × factor^L / SPEED / (1+R)` |

三项结构性缺失：
1. **无 `2^N` 纳米工厂项** —— `BUILDINGS` 无 id 34，`buildingTime()` 签名也无 `nanite` 参数
2. **无 `T_min` 下限**
3. **不由造价推导** —— 每种建筑一个手写 `baseTime` 常量

量化后果（Lv0、speed=4、机器人=0）：

| 建筑 | 线上 | F-08 应有 | 倍率 |
|---|---|---|---|
| 金属矿 | 15.0s | 27.0s | 1.80 |
| 聚变反应堆 | 22.5s | 453.6s | 20.16 |
| 月球基地 | 15.0s | 5,760.0s | 384 |
| 传感器阵列 | 15.0s | 21,600.0s | 1,440 |
| 导弹发射井 | 15.0s | 14,400.0s | 960 |
| **跳跃门** | **15.0s** | **2,160,000.0s（25 天）** | **144,000** |

**线上 Lv0 有 15 个建筑都是 15 秒，只有聚变是 22.5 秒**——最贵的跳跃门和最便宜的金属矿耗时相同。
「越贵越慢」的设计意图在实现中完全不存在。

```powershell
python tools/verify_f08_vs_impl.py
# 2026-09-28 已裁决为方案 B，F-08 降级 Frozen -> Candidate，脚本转为 exit 0
# （仍完整报告三项差距，但不再判定为缺陷——线上常量节奏是 v1.0.0 已发布的设计）
```

**裁决（2026-09-28）：方案 B —— 改声明，不改代码。**

理由：
- **v1.0.0 已发布**（tag `v1.0.0`），改建造时长会破坏存量存档的建造队列计时；
- 改公式 = 改全部平衡，且需连带实现纳米工厂 id 34（其造价 1M/500K/100K，
  会重排整个中后期节奏）；
- 改声明是**零风险的诚实修正**——让文档承认线上实际用什么。

已执行：
- `balance_rc1.json` 的 F-08：`status` 由 `Frozen` 降为 `Candidate`，
  `expression` 标注「仅线下推演用」，`source` 写明线上实际是
  `baseTime*factor^L/SPEED/(1+R)`、无 `2^N`、无 `T_min`；
- `meta.hash` 按 `config_validate.py` 输出口径回填（旧值记入 `meta.notes` 供追溯）；
- `tools/verify_f08_vs_impl.py` 改为按 `status` 分级：`Frozen` 时严格判定并 exit 1，
  非 Frozen 时退化为差距报告并 exit 0。

**连带影响**：`doc/balance-content-check-2026-09-24.md` 与 CR-002 附录 B 的 SIM 数字
（资产 188006 / 182659、仓损 0.095 / 0.081、低能占比 0.381→0.135 等）
是用 `rules/formulas.py` 的 F-08 模型离线算的。它们**仍然有效**，但适用范围是
「同一模型下的方案对照」——可用于比较 A/B 优劣，**不能**用于论证线上数值已校准。
使用这些数字时必须带这句限定。

### 2026-09-28 修正：脚本此前在给假 PASS

原版脚本的差异扫描只比**「代码 vs 经典 0.84」一个维度**，且循环开头有
`if bid in ALLOW: continue`，连带把 RC1 维度一起跳过了。后果：

- **id 12 聚变的「RC1 150/60/30 vs 代码 900/360/180」这类冲突被完全漏检**
  —— 因为聚变的代码值恰好与经典原版一致，一比就过；
- **RC1 漏登记的 4 个建筑查不出来**：33 地形改造器、42 传感器阵列、43 跳跃门、
  44 导弹发射井（RC1 均无对应键，代码已实现且值同原版）。

而「RC1 冻结值 vs 代码实际值」恰恰是**唯一会让人按规则集调参踩空**的维度。

改为三维度扫描（代码↔经典 / 代码↔RC1 / RC1↔经典）后，脚本立刻暴露出
这 4 项登记缺口并已补进 ALLOW。变异测试确认：删掉 id 12 的 ALLOW 后，
脚本精确报出「RC1 冻结值 150/60/30 g1.5 与代码 900/360/180 f1.8 不符」并 exit 1。
